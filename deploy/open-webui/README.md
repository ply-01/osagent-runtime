# OSagent + Open WebUI

This deployment runs a user-facing Open WebUI and one independently persisted
OSagent memory service. The same Compose file is used on Windows Docker Desktop
and on a Kylin Linux virtual machine.

## Architecture

```text
Browser -> Open WebUI -> chat model (OpenAI-compatible or Ollama)
                    |-> OSagent MCP: memory operations + workspace file write
                    `-> memory Filter: recall before, observe after each turn
```

The service exposes nine MCP tools: service capabilities, agent run, four
explicit memory operations, a workspace-scoped UTF-8 file writer, a hash-verified
plugin marketplace, and a constrained Qianxin trusted-browser controller. Automatic turn observation is an internal
authenticated REST endpoint, not an LLM tool.

The main conversation is generated by Open WebUI's selected model. The separate
`OS_AGENT_*` model settings are used only when that model calls `os_agent_run`.

## Start on Windows

Use PowerShell from the repository root:

```powershell
Set-Location deploy/open-webui
./init.ps1
# Edit .env to select the chat and embedding endpoints.
./configure-from-osagent.ps1 # optional: reuse config/llm.local.json
docker compose config
docker compose up -d --build
docker compose ps
```

Open `http://localhost:3000`.

The default is personal single-user mode (`WEBUI_AUTH=False`). Do not change an
existing Open WebUI data volume between authenticated and unauthenticated mode.
This OSagent memory store is also single-user; a multi-user deployment requires
one memory namespace or service per user before enabling sign-ups.

## Connect the nine LLM tools

When `OPEN_WEBUI_IMAGE` points to the OSagent customized image, startup restores
the managed OSagent MCP connection from `OS_AGENT_MEMORY_URL` and
`OS_AGENT_MEMORY_API_KEY`; no chat-composer switch is required. The untouched
upstream image does not contain that startup integration, so use the following
manual procedure for an upstream-only deployment:

In Open WebUI v0.11.0:

1. Open Admin Settings, then External Tools, and add a server.
2. Choose `MCP (Streamable HTTP)`.
3. Set the URL to `http://osagent-memory:8765/mcp`.
4. Add header `Authorization: Bearer <OS_AGENT_MEMORY_API_KEY>`.
5. Verify that the nine `os_agent_*` tools are listed and save the server.
6. The OSagent MCP server is enabled globally; no OSagent extension panel or
   chat-composer switch is required. Open WebUI prefixes callable names with
   the server ID, for example `osagent_memory_os_agent_memory_recall`.

Memory deletion is a soft delete. Hard deletion is intentionally not exposed to
the LLM.

`os_agent_file_write` supports `create`, `overwrite`, and `append`, accepts only
paths relative to `OS_AGENT_WORKSPACE`, rejects path escapes, and limits each
call to 1 MiB of UTF-8 content. The Compose deployment enables it explicitly.
Point `OS_AGENT_WORKSPACE` at a dedicated user workspace rather than a directory
containing secrets or system configuration.

The plugin marketplace reads a local catalog from
`<OS_AGENT_MCP_MEMORY_ROOT>/../plugins/catalog.json` (or the path in
`OS_AGENT_PLUGIN_CATALOG`). A remote entry uses an HTTPS `download_url` and a
lowercase SHA-256 digest. A catalog imported from `openai/plugins` instead uses
a relative `source_path` below the fixed local source root and records its Git
revision. Installation is disabled by default. To permit an
administrator-approved install, set `OS_AGENT_PLUGIN_INSTALL_ENABLED=true` in
the service environment. Bundles are limited to 100 MiB; remote archives get
checksum and traversal checks, while local sources get path-boundary and
symbolic-link checks. OSagent never imports or executes installed code.

An installed bundle is not automatically callable. The customized
**Workspace -> Plugins** page inspects each enabled bundle. A bounded `SKILL.md`
is exposed as declarative guidance; a credential-free remote HTTPS MCP
declaration can be verified and registered with Open WebUI. For an OAuth 2.1
plugin such as Linear, click **Connect**, complete the provider consent page,
and return to a chat with the plugin tool selected. OAuth tokens remain in the
signed-in Open WebUI user's store and are never returned to OSagent. Local
command declarations, plain HTTP endpoints, and declarations containing static
headers or environment secrets are rejected from automatic connection.

The native service also serves a one-click administration page at
`http://127.0.0.1:8765/plugins`. When the service is inside a VM, use an
SSH local tunnel and open the forwarded `127.0.0.1:33002/plugins` URL. Enter
the service API key to list catalog entries and install, enable, disable, or
uninstall them. Installed state is persisted in
`plugins/marketplace-state.json` and is independent of Open WebUI's own
extension or Memory features.

Computer Use is exposed as a separate backend tool with a browser target and a
desktop target. Browser actions require `OS_AGENT_COMPUTER_USE_ENABLED=true`,
an explicit executable or a detected Qianxin desktop entry, and a Chromium
DevTools endpoint. Desktop actions use the logged-in graphical session's
xdotool/ydotool and screenshot backend. Both targets remain disabled until the
authenticated backend policy explicitly enables them; the chat composer has no
Computer Use switch. Browser `allowlist`, `public`, and `unrestricted` modes
continue to enforce their origin policy; they do not grant desktop access.
Desktop coordinates and text are bounded and never become shell commands.

## Enable automatic memory

Open Workspace, create a Function, and load the contents of
`/opt/osagent-integrations/osagent_memory_filter.py`. Enable it globally or only
for the desired model. Its default endpoint and key come from the container
environment, so no secret needs to be pasted into the Function source.

The Compose deployment makes OSagent the authoritative memory backend and
disables Open WebUI's built-in Memories, Memory System Context, Background
Review, and Notes features. Do not re-enable those features in Admin Settings:
they use Open WebUI's independent database, would not appear in OSagent, and
could cause duplicate writes or conflicting context.

The Open WebUI Memory page is therefore not an OSagent management screen.
Automatic recall and persistence run through the OSagent Filter, while explicit
inspection and changes use the nine MCP tools. OSagent memory remains in the
separate `osagent-memory-data` volume.

The Filter recalls relevant records before each model request and injects them
as untrusted evidence. After a completed response, it sends the user/assistant
turn to the memory extractor. Background requests such as title, tag, query, and
autocomplete generation are ignored. Failures are fail-open by default, so an
embedding or memory outage does not take down chat.

The Compose file pins the `v0.11.0-slim` image. OSagent owns the memory
embedding path, so Open WebUI's pre-bundled Whisper and embedding models are not
required. Open WebUI features that need those models may download them on first
use.

## Move to Kylin

Install Docker Engine and the Compose plugin in the Kylin VM, copy this
repository, and update only these `.env` values:

```dotenv
OS_AGENT_WORKSPACE=/home/veritas/OSagent
OPENAI_API_BASE_URL=http://host.docker.internal:11434/v1
OS_AGENT_EMBEDDING_BASE_URL=http://host.docker.internal:11434/v1
```

Create the initial file with `sh deploy/open-webui/init.sh` before editing it.

Then run the same `docker compose up -d --build`. The published WebUI address is
`http://<kylin-vm-ip>:3000`; the memory API remains bound to the VM loopback and
is reached by Open WebUI over the private Compose network.

Keep `WEBUI_SECRET_KEY`, `OS_AGENT_MEMORY_API_KEY`, `osagent-open-webui-data`,
and `osagent-memory-data` when migrating. Those two named volumes contain the UI
database and OSagent memory respectively.

Create a consistent backup while the services are briefly stopped:

```powershell
./backup.ps1
```

On Kylin use `sh backup.sh`. The restore scripts always create new named volumes
and refuse to overwrite an existing volume. After restoring, set the two volume
names printed by the script in `.env`, then start Compose normally.
